            DataCanon

            DataCanon provides a canonical semantic language for structured scientific data.

            Rather than preserving implementation-specific representations, DataCanon assigns structured scientific data a deterministic, language-independent identity.

            The project provides

            • the DataCanon language specification,
            • an immutable semantic model,
            • a parser,
            • a canonical renderer,
            • deterministic fingerprinting,
            • native HDF5 persistence,
            • a Python reference implementation.

            DataCanon is designed to provide

            • deterministic semantic identity,
            • stable long-term persistence,
            • implementation-independent interchange,
            • meaningful version control history,
            • robust foundations for scientific software.

            Philosophy

            Conventional serialization formats preserve representations.

            DataCanon preserves semantics.

            Every semantic object has exactly one canonical representation, independent of programming language or persistence mechanism.

            DataCanon intentionally focuses on representing data rather than manipulating it. It performs no symbolic algebra or computation and defines only the semantic objects needed to faithfully represent scientific data.

            Relationship to Other Projects

            DataCanon serves as the semantic foundation for the Principia Materia ecosystem.

            In particular,

            • DataSchemer provides human-oriented configuration, validation, and data modeling.
            • DataCanon provides canonical semantic identity, fingerprinting, and persistence.
            • Principia Materia builds long-lived scientific workflows on top of these foundations.

            Although developed for Principia Materia, DataCanon is intended to be useful whenever scientific data must remain stable and reproducible over long periods of time.

            Status

            DataCanon Version 1 is under active development.

            The semantic model, parser, renderer, fingerprinting, and HDF5 persistence are implemented in the Python reference implementation. The language specification continues to evolve as practical experience is gained.

            1 - Getting Started

            Getting Started

            DataCanon is a language for representing structured scientific data.

            Its purpose is simple:

            Assign semantic data a deterministic, language-independent identity.

            DataCanon provides

            • a formal language,
            • a parser,
            • a canonical renderer,
            • deterministic fingerprinting,
            • native HDF5 persistence,
            • a Python reference implementation.

            It is intended for scientific software whose data must remain stable and reproducible over many years.

            Installation

            Clone the repository, build virtual environment, install using pip. A makefile is included for clarity.

            Canonical Rendering

            Canonical rendering converts ordinary Python objects into deterministic DataCanon text.

            import numpy as np

from data_canon import render

data = {
  "lattice_list":
    [
      [3.913, 0.0, 0.0],
      [0.0, 3.913, 0.0],
      [0.0, 0.0, 3.913],
    ],

  "lattice_array":
    np.array(
      [
        [3.913, 0.0, 0.0],
        [0.0, 3.913, 0.0],
        [0.0, 0.0, 3.913],
      ]
    ),

  "temperature": 300,
}

print(render(data))

            produces

            {
  "lattice_list":
    [
      [3.913, 0.0, 0.0],
      [0.0, 3.913, 0.0],
      [0.0, 0.0, 3.913]
    ],
  "lattice_array":
    array(
      [[3.913, 0.0, 0.0],
       [0.0, 3.913, 0.0],
       [0.0, 0.0, 3.913]]
    ),
  "temperature": 300
}

            Fingerprinting

            Every semantic object possesses a deterministic fingerprint.

            from data_canon import fingerprint

digest = fingerprint(data)

# print (digest)
# fb6c431a58b65d1cfb06849276e7aa132e8e925698cde1c6d9c2af5b24105bfb

            The fingerprint is computed from the canonical DataCanon representation.

            Equivalent semantic objects always produce identical fingerprints.

            HDF5 Persistence

            DataCanon also provides native HDF5 persistence.

            from data_canon import (
  write_hdf5,
  read_hdf5,
)

write_hdf5(
  data,
  "example.h5",
)

restored = read_hdf5(
  "example.h5",
)

            The restored object is semantically identical to the original.

            Expressive Data Input

            Although DataCanon is designed to provide deterministic semantic identity, it is also a practical language for entering structured scientific data.

            Unlike JSON or YAML, DataCanon directly represents many scientific data types.

            For example, Version 1 provides native support for

            • tuples,
            • dense multidimensional arrays,
            • exact fractions,
            • radicals,
            • complex floating-point values.

            These objects are represented directly rather than reconstructed through application-specific conventions.

            Because these are semantic objects rather than conventions layered on top of lists or strings, every conforming implementation interprets them identically.

            Applications that already use DataSchemer or other schema-based validation can accept DataCanon directly as an input language while preserving the full semantic structure of the data.

            Relationship to DataSchemer

            DataCanon and DataSchemer solve different problems.

            DataSchemer assigns semantics to ordinary Python data through schemas and validation.

            DataCanon preserves those semantics through deterministic rendering, fingerprinting, and persistence.

            The two projects are designed to work together, but either may be used independently.

            3 - Specifications

            Version 1 Draft

            1. Introduction

            DataCanon (DC) is a formal language for representing structured scientific data.

            Its primary purpose is to assign a deterministic, language-independent semantic identity to scientific data. A DataCanon document may be rendered as human-readable text, fingerprinted, or stored using alternative persistence mechanisms while preserving identical semantics.

            The reference implementation realizes the DataCanon semantic model using the Data Skeleton, an immutable intermediate representation implemented in Python.

            DataCanon is intended for scientific software whose data must remain stable, portable, reproducible, and meaningful over years or decades of development.

            2. Goals

            DataCanon is designed to solve four practical engineering problems.

            • deterministic rendering
            • deterministic fingerprinting
            • language-independent interchange
            • long-term persistence

            These goals support scientific software whose data must remain robust over the lifetime of a project rather than the lifetime of a particular programming language or serialization format.

            3. Non-Goals

            DataCanon intentionally does not provide

            • symbolic algebra
            • computation
            • variables
            • user-defined functions
            • expression evaluation
            • units
            • dimensional analysis

            DataCanon represents immutable semantic data.

            It does not manipulate data.

            4. Semantic Model

            Every valid DataCanon document denotes a tree of immutable semantic objects.

            Version 1 defines the following semantic objects.

            SyntaxSemantic Object
            42Integer scalar
            3.14Floating-point scalar
            "hello"String scalar
            trueBoolean scalar
            falseBoolean scalar
            nullNull scalar
            1/3Fraction
            1/2 * sqrt(3)Radical
            complex(1.0, 2.0)Complex floating-point value
            [ ... ]List
            ( ... )Tuple
            { ... }Set
            { key: value }Mapping
            array(...)Dense multidimensional array

            The current Python reference implementation realizes these semantic objects using the Data Skeleton.

            The implementation is informative.

            The semantic model is normative.

            5. Design Principles

            DataCanon satisfies the following fundamental properties.

            Deterministic

            Every semantic object has exactly one canonical textual representation.

            Equivalent semantic objects always render identically.

            Lossless

            Parsing followed by rendering preserves semantics.

            DataCanon
     │
     ▼
 Parser
     │
     ▼
Semantics
     │
     ▼
Renderer
     │
     ▼
DataCanon

            The semantic object obtained by parsing a valid DataCanon document is preserved under render/parse round trips.

            Language Independent

            The language specification is independent of Python or any other implementation language.

            Multiple implementations may realize the same semantic model while preserving identical DataCanon documents.

            Stable

            The language specification evolves independently of any persistence mechanism.

            The same semantic object may be represented as

            • canonical DataCanon text,
            • HDF5,
            • future persistence formats,

            without changing its meaning.

            Minimal

            The language intentionally defines exactly one canonical representation for each semantic object.

            The language favors simple, deterministic rules over expressive but ambiguous alternatives.

            6. Primitive Objects

            Integer

            Integers denote exact mathematical integers.

            Integers have unlimited precision.

            Float

            Floating-point literals denote IEEE-754 binary64 values.

            Floating-point values are inherently approximate.

            Applications requiring exact arithmetic should instead use Fractions.

            Negative Numeric Literals

            Integer, floating-point, and fraction literals may be preceded by a leading minus sign.

            For example,

            -42

-3.14

-1/2

            Negative coefficients may likewise be used when constructing Radicals.

            -2 * sqrt(3)

-1/2 * sqrt(3)

-1.89 * sqrt(3)

            DataCanon defines negative numeric literals.

            It does not define a general unary negation operator.

            Consequently,

            -sqrt(2)

            is not valid DataCanon syntax.

            The equivalent canonical representation is

            -1 * sqrt(2)

            String

            Strings are enclosed by double quotation marks.

            Single-quoted strings are not part of Version 1.

            Boolean

            Boolean literals are

            true
false

            Null

            The null literal is

            null

            7. Atomic Objects

            Atomic semantic objects represent values that are conceptually indivisible.

            They render on a single line.

            Fraction

            Fractions represent exact rational values.

            Fractions consist of an integer numerator and denominator.

            Fractions are semantic objects.

            They are not arithmetic expressions.

            Radical

            Radicals represent an optional floating-point coefficient, an optional rational coefficient, and a square root.

            Examples include

            sqrt(2)

2 * sqrt(2)

1/2 * sqrt(3)

1.89 * sqrt(3)

1.89 * 1/2 * sqrt(3)

            The * operator has no meaning outside Radical syntax.

            DataCanon defines no general multiplication operator.

            Radicals are real-valued semantic objects.

            Complex

            Complex values represent floating-point complex numbers.

            A Complex consists of two binary64 floating-point values representing the real and imaginary components.

            Complex values are written

            complex(1.0, 2.0)

complex(1, -3.5)

            Integer literals are permitted and are converted to floating-point values.

            The canonical renderer always emits floating-point literals.

            Complex values are atomic semantic objects.

            They are not arithmetic expressions.

            8. Composite Objects

            Lists

            Lists are ordered collections.

            Lists are written

            [ ... ]

            Tuples

            Tuples are ordered immutable collections.

            Tuples are written

            ( ... )

            Parsers may accept an optional trailing comma.

            Renderers always emit the canonical form without a trailing comma.

            Sets

            Sets are unordered collections.

            Sets are written

            { ... }

            The empty set is written

            emptyset

            Implementations render Set elements in canonical order.

            Mappings

            Mappings associate keys with values.

            Mappings preserve insertion order.

            Arrays

            Arrays represent dense multidimensional numerical data.

            Arrays are distinct semantic objects from Lists.

            Lists represent arbitrary recursive structure.

            Arrays represent regular multidimensional tensors.

            Arrays are homogeneous.

            Version 1 supports arrays whose element type is

            • integer64
            • float64
            • complex128

            Structural Representation

            Small arrays are rendered structurally.

            For example,

            array(
  [[1.0, 2.0],
   [3.0, 4.0]]
)

            Binary Representation

            Large arrays are rendered using a canonical binary representation.

            For example,

            array(
  binary(
    "float64",
    (1001),
    "0123456789abcdef..."
  )
)

            The threshold separating structural and binary rendering is defined by this specification.

            The binary representation exists to provide deterministic rendering for machine-scale numerical data while avoiding the cost of rendering very large arrays as decimal text.

            The canonical binary representation consists of

            • the canonical element type,
            • the canonical array shape,
            • a little-endian byte stream,
            • C-contiguous storage order.

            The resulting byte stream is represented as hexadecimal text.

            Both structural and binary representations denote identical semantic objects.

            9. Rendering

            Rendering is deterministic.

            The renderer produces the canonical textual representation of a semantic object.

            Rendering is optimized for

            • determinism,
            • stability,
            • reasonable readability,

            rather than sophisticated document formatting.

            Atomic semantic objects render on a single line.

            Composite semantic objects introduce structural formatting.

            10. Fingerprinting

            Every semantic object possesses a deterministic fingerprint.

            Fingerprints are computed directly from the UTF-8 encoding of canonical DataCanon text.

            Semantic Object
       │
       ▼
Canonical DataCanon
       │
       ▼
UTF-8
       │
       ▼
SHA-256

            The fingerprint therefore identifies the semantic object itself rather than any particular implementation.

            11. Persistence

            Canonical DataCanon text is itself a complete persistence format.

            Alternative persistence mechanisms may preserve identical semantics while optimizing different engineering objectives.

            For example,

            PersistenceOptimizes
            DataCanonreadability, version control, deterministic identity
            HDF5storage efficiency, random access, compression, high-performance numerical I/O

            Persistence mechanisms preserve the same semantic model.

            They differ only in what they optimize.

            12. Conformance

            A conforming implementation MUST

            • accept valid DataCanon,
            • construct the correct semantic model,
            • render canonical DataCanon,
            • preserve semantics under parse/render round trips.

            A conforming renderer MUST always produce canonical DataCanon.

            A conforming parser MAY accept non-canonical input provided the resulting semantic object is unchanged.
