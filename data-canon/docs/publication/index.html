    1. DataCanon
    2. Publication Outline

    Publication Outline

    A possible journal would be The Journal of Open Source Software.

    Working Title

    DataCanon: Deterministic Semantic Identity for Structured Scientific Data

    Alternative titles:

    • DataCanon: A Canonical Language for Structured Scientific Data
    • DataCanon: Language-Independent Identity and Persistence for Scientific Data
    • Canonical Semantic Representation of Structured Scientific Data

    Central Thesis

    Scientific software requires more than serialization.

    A scientific data object should possess a stable identity that is independent of

    • programming language,
    • in-memory representation,
    • persistence mechanism,
    • formatting choices,
    • and the lifetime of a particular software implementation.

    DataCanon addresses this problem by defining a small formal language in which each supported data instance has a unique canonical textual representation, the DataCanon Value (DCV).

    The DCV provides a language-independent semantic identity from which deterministic fingerprints, interchange formats, and persistence mechanisms can be derived.

    1. Introduction

    1.1 The problem

    Scientific software routinely stores structured data containing objects such as

    • integers and floating-point values,
    • exact rational numbers,
    • structured irrational coefficients,
    • complex values,
    • multidimensional numerical arrays,
    • tuples and lists,
    • sets,
    • mappings with structured keys.

    Existing serialization and persistence formats solve important parts of this problem but generally do not define a single canonical semantic identity for such data.

    Questions that arise in long-lived scientific software include:

    • When are two independently constructed data objects identical?
    • Can that identity survive a change of programming language?
    • Can the same identity survive migration between text, HDF5, databases, or future persistence mechanisms?
    • Can the identity be fingerprinted deterministically?
    • Can exact mathematical structure be preserved without introducing a symbolic algebra system?

    1.2 DataCanon

    Introduce DataCanon as a formal language for structured scientific data.

    Central idea:

    data instance
     ↓
canonical representation
     ↓
DataCanon Value
     ↓
deterministic fingerprint

    Emphasize that DataCanon separates semantic identity from

    • storage,
    • computation,
    • implementation language,
    • and human-oriented input conventions.

    1.3 Contributions

    Possible contribution list:

    1. A formal canonical language for structured scientific data.
    2. Explicit semantic types designed for scientific applications.
    3. Deterministic canonical representation and fingerprinting.
    4. Preservation of exact numerical structure without symbolic evaluation.
    5. Explicit distinction between ordered and unordered collections.
    6. A practical portable model for multidimensional machine arrays.
    7. Lossless interchange with alternative persistence formats.
    8. A Python reference implementation.
    9. A language-independent conformance suite.
    10. Independent Python and Julia implementations demonstrating cross-language canonical identity.

    Items 9 and 10 depend on completion of the proposed Julia implementation.

    2. Design Requirements

    Describe the engineering requirements that motivated DataCanon.

    2.1 Determinism

    Every instance of a DataCanon semantic type has exactly one DCV.

    2.2 Language independence

    Canonical identity should not depend on Python or another implementation language.

    2.3 Losslessness

    Semantic distinctions represented by DataCanon must survive parsing, rendering, interchange, and persistence.

    2.4 Long-term stability

    Scientific data may outlive

    • particular source-code versions,
    • serialization libraries,
    • programming languages,
    • and storage technologies.

    2.5 Human readability

    Canonical text should remain reasonably readable for small and moderate data structures.

    2.6 Practicality

    Language independence must not require DataCanon to replace mature native facilities such as numerical array implementations.

    Discuss the distinction between principled portability and impractical abstraction.

    2.7 Non-goals

    DataCanon does not provide

    • symbolic algebra,
    • expression evaluation,
    • variables,
    • functions,
    • units,
    • dimensional analysis,
    • or general computation.

    Key principle:

    DataCanon canonicalizes representation, not mathematics.

    3. DataCanon Language Model

    3.1 DataCanon Source

    Define DataCanon Source (DCS) and valid DCS.

    Multiple valid source strings may differ textually.

    Example:

    [1,2,3]

    and

    [ 1, 2, 3 ]

    3.2 DataCanon Value

    Define:

    DataCanon Value (DCV): Canonical DataCanon text encoding exactly one instance of a DataCanon semantic type.

    Two DCVs are equal if and only if their text is identical.

    3.3 Parsing and rendering

    Valid DCS
   ↓
 parsing
   ↓
semantic instance
   ↓
 rendering
   ↓
  DCV

    For a DCV,

    render(parse(DCV)) = DCV

    3.4 Canonical identity

    Explain why textual identity provides a simple implementation-independent definition of equality.

    4. Semantic Types

    Present the Version 1 semantic types and motivate distinctions that are important for scientific data.

    4.1 Primitive scalar types

    • Integer
    • Float
    • String
    • Boolean
    • Null

    4.2 Fraction

    Example:

    1/2

    Discuss preservation of numerator and denominator.

    Important example:

    1/2

    and

    2/4

    are distinct DCVs.

    DataCanon does not perform rational reduction.

    4.3 Coefficient

    Examples:

    sqrt(3)

1/2 * sqrt(3)

1.89 * 1/2 * sqrt(3)

1/4 + 0.199

    Explain the motivation for preserving structured irrational numerical data.

    Emphasize that * and + are structural syntax rather than general arithmetic operators.

    4.4 Complex

    Complex values compose two real-valued numerical DataCanon instances.

    Example:

    complex(1/2, 1/2 * sqrt(3))

    Use this as a central scientific example.

    Discuss exact representation of complex phase factors and other quantities that would otherwise be prematurely converted to floating point.

    4.5 Ordered composite types

    List

    Ordered recursive collection.

    Tuple

    Ordered immutable structural collection.

    Explain why List and Tuple remain semantically distinct.

    4.6 Unordered collections

    Set

    Semantically unordered but stored/rendered in canonical semantic order.

    Explain distinction between semantic order and canonical order.

    4.7 Mappings

    Mapping

    Entry order participates in semantic identity.

    UnorderedMapping

    Entry order does not participate in semantic identity.

    Entries are nevertheless stored and rendered in canonical semantic order.

    This section provides a useful illustration of the distinction between

    • semantic ordering,
    • insertion ordering,
    • canonical ordering.

    5. Arrays

    This should probably be a substantial section because Arrays illustrate one of the central design compromises in DataCanon.

    5.1 Motivation

    Scientific software requires efficient multidimensional machine arrays.

    Treating every Array element as an independent recursively typed DataCanon instance would impose unnecessary restrictions and overhead.

    5.2 Array construction and semantic identity

    DataCanon deliberately does not prescribe all native Array construction and coercion policies.

    Array construction may therefore depend on the underlying language implementation.

    Once a portable Array representation exists, however, its canonical identity is specified by DataCanon.

    5.3 Portable Array types

    Version 1 standardizes portable representations for

    • bool
    • int8, int16, int32, int64
    • uint8, uint16, uint32, uint64
    • float16, float32, float64
    • complex64, complex128

    Arrays with the same portable Array type, shape, and element values must produce identical DCVs across conforming implementations.

    5.4 Structural representation

    Arrays containing at most 1000 elements are represented structurally.

    Example:

    array(
  [[1.0, 0.0],
   [0.0, 1.0]]
)

    Explain that the brackets inside array(...) describe Array structure and do not construct nested DataCanon Lists.

    Complex machine-array values use compact Array syntax such as

    1.0+2.0j

    which is distinct from the structured DataCanon Complex type.

    5.5 Binary representation

    Arrays containing more than 1000 elements use canonical binary representation.

    Example:

    array(
  binary(
    "float64",
    (1001),
    "..."
  )
)

    Specify

    • portable dtype,
    • shape,
    • C-contiguous ordering,
    • canonical little-endian byte order,
    • hexadecimal encoding.

    5.6 Why not nested Lists?

    Nested Lists remain available when every element must retain independently defined DataCanon semantics.

    This provides an explicit escape hatch from implementation-dependent Array construction.

    6. Canonical Ordering

    Describe the semantic ordering used to canonicalize intrinsically unordered types.

    Applications include

    • Set,
    • UnorderedMapping,
    • future unordered semantic types.

    Explain that canonical ordering is not mathematical ordering and carries no application-specific interpretation.

    Its purpose is solely to produce deterministic representation.

    7. Fingerprinting and Semantic Identity

    A fingerprint is computed from the UTF-8 encoding of the DCV.

    semantic instance
       ↓
      DCV
       ↓
     UTF-8
       ↓
    SHA-256

    Consequences:

    • fingerprinting requires no independent semantic rules,
    • identical DCVs necessarily produce identical fingerprints,
    • fingerprint identity is independent of persistence mechanism.

    Discuss ordered versus unordered mapping fingerprints as an illustrative example.

    8. Human-Oriented Input and Rendering

    Canonical representation need not be the most convenient representation for humans.

    8.1 Pretty rendering

    Describe alignment and compact formatting.

    Pretty output remains valid DCS but need not itself be a DCV.

    8.2 Augmented parsing

    Describe the separation between canonical language and input conveniences.

    Features include

    • internal substitutions,
    • external substitutions,
    • mathematical substitutions,
    • List Shorthand.

    Emphasize that augmented parsing does not enlarge the canonical DataCanon language.

    9. Interchange and Persistence

    9.1 YAML interchange

    Discuss ordinary YAML for types YAML represents faithfully and explicit DC> escapes for richer DataCanon values.

    Example:

    fraction: DC> 1/2
phase: DC> complex(1/2, 1/2 * sqrt(3))

    Discuss structured Mapping keys as an example of a semantic distinction that ordinary YAML workflows may handle awkwardly.

    9.2 HDF5 persistence

    Describe recursive preservation of DataCanon semantic types.

    Explain why persistence is deliberately separated from canonical identity.

    9.3 DataCanon text as persistence

    The DCV itself is a complete textual persistence representation.

    Alternative persistence formats optimize different engineering goals while preserving DataCanon identity.

    10. Python Reference Implementation

    Keep this section relatively short. The paper is about DataCanon rather than the Python package.

    10.1 Data Skeleton

    The Python implementation uses an immutable intermediate representation called the Data Skeleton.

    Emphasize that the Data Skeleton is an implementation detail rather than part of the DataCanon language specification.

    10.2 Native Python types

    The reference implementation supplies native Python types where standard Python types do not adequately represent DataCanon semantics:

    • Coefficient
    • ComplexNumber
    • UnorderedDict

    Explain the distinction between DC representation and Python mathematical behavior.

    For example,

    complex(1/2, 1/2 * sqrt(3))

    maps losslessly to a Python ComplexNumber.

    Explicit conversion to built-in Python complex may introduce floating-point approximation.

    10.3 Conversion boundary

    Discuss explicit conversion:

    Python ↔ Data Skeleton ↔ DataCanon

    and why parsing and Python conversion are deliberately separate operations.

    11. Cross-Language Conformance

    This section becomes particularly important if the Julia implementation is completed.

    11.1 Julia implementation

    Describe an independent implementation of the normative DataCanon core in Julia.

    The implementation need not reproduce Python-specific API choices.

    11.2 Shared conformance corpus

    Construct an implementation-independent corpus containing

    • valid DCS,
    • expected DCV,
    • expected fingerprint.

    Both Python and Julia implementations operate independently on the same corpus.

    11.3 Cross-language results

    Demonstrate byte-for-byte agreement of DCVs and fingerprints.

    Particularly important cases:

    • Fraction,
    • Coefficient,
    • structured Complex,
    • Set canonical ordering,
    • Mapping and UnorderedMapping,
    • every portable Array dtype,
    • structural Arrays,
    • binary Arrays,
    • multidimensional shapes,
    • signed zero and floating-point edge cases.

    11.4 Native Array interoperability

    Construct equivalent Arrays natively in Python/NumPy and Julia and demonstrate identical DCVs.

    Examples:

    NumPy Float32 ↔ Julia Float32
NumPy Int32   ↔ Julia Int32
NumPy UInt64  ↔ Julia UInt64

    This provides direct experimental evidence for DataCanon’s language-independence claims.

    12. Comparison with Existing Approaches

    This section requires a proper literature review before writing.

    Potential comparisons include

    • JSON and canonical JSON schemes,
    • YAML,
    • CBOR and deterministic/canonical CBOR,
    • MessagePack,
    • Protocol Buffers or related schema-driven formats,
    • HDF5,
    • scientific data standards where relevant,
    • content-addressable and canonical serialization systems.

    The comparison should distinguish several separate concerns:

    • serialization,
    • canonical identity,
    • scientific semantic types,
    • exact numerical structure,
    • persistence,
    • human readability,
    • language independence.

    Avoid claiming that competing formats are deficient merely because they solve a different problem.

    The central comparison should be:

    DataCanon is designed primarily to assign deterministic semantic identity to structured scientific data; serialization and persistence follow from that identity.

    14. Limitations and Future Work

    Possible topics:

    • additional portable Array representations,
    • additional language implementations,
    • evolution and versioning of the specification,
    • larger conformance suites,
    • schema systems layered above DataCanon,
    • integration with databases and content-addressed storage,
    • performance characterization.

    Emphasize that computation and symbolic mathematics remain intentionally outside the DataCanon language.

    15. Conclusion

    Restate the central separation:

    semantic identity
      ≠
storage format
      ≠
programming-language representation
      ≠
mathematical computation

    DataCanon defines a canonical semantic identity for structured scientific data while permitting implementations and persistence mechanisms to optimize their own concerns.

    If demonstrated with independent Python and Julia implementations, emphasize that canonical identity is determined by the specification rather than by either implementation.
