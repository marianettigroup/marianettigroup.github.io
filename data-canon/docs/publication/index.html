    1. DataCanon
    2. Publication Outline

    Publication Outline

    This outline proposes a paper for the Journal of Open Source Software (JOSS) describing DataCanon and its Python reference implementation.

    The paper should explain the research problem, the software’s contribution, and the evidence supporting its use. The seven specifications and documentation carry the detailed type definitions, encoding rules, and API reference.

    Working title

    DataCanon: Deterministic Identity and Persistence for Structured Scientific Data

    An alternative retaining the original emphasis is:

    DataCanon: Deterministic Semantic Identity for Structured Scientific Data

    A different choice which tries to capture the versatility for exploring data.

    DataCanon: The Last Mile of Scientific Data

    Canonical Identity Across Programming Languages and Storage Formats

    Central thesis

    Scientific software needs to preserve complex structured data across changes in programming language, software implementation, and storage format. DataCanon gives that data an explicit, portable identity model and supplies software for constructing, communicating, fingerprinting, and persisting it.

    DataCanon defines DataCanon Types (DCTs), their valid DataCanon Instances (DCIs), and their equality relations. Every DCI has a unique canonical byte encoding. Human-readable Shorthand, YAML interchange, and HDF5 represent that same data without defining its identity.

    The scientific motivation should lead: exact numerical structures built from Fractions, Products, Powers, Sums, and Quotients, structured Complex values, typed multidimensional Arrays, and reliable persistence of nested scientific data. The paper should then explain how canonical identity makes those structures portable and reproducibly identifiable.

    JOSS format and scope

    The current JOSS paper guidance sets a 750–1,750-word range and identifies sections for Summary, Statement of need, State of the field, Software design, Research impact statement, AI usage disclosure, Acknowledgements, and References.

    Organize the manuscript around those sections. Aim for approximately 1,400–1,600 words of prose, leaving room to adjust the emphasis during writing. The word allocations below are planning targets, not journal requirements.

    SectionApproximate words
    Summary150
    Statement of need250
    State of the field250
    Software design450
    Research impact statement250
    AI usage disclosure and Acknowledgements100

    The submitted paper concerns usable research software. The Python package, its tests, documentation, and scientific applications should therefore have a substantial role. An independent Julia implementation would strengthen the portability evidence, but should be described as completed work only when it has been implemented and validated.

    1. Summary

    Introduce DataCanon in language accessible to a researcher who has never used it. Explain that it allows complex scientific data to be written, recovered, compared, and fingerprinted using an identity model independent of storage layout and implementation language.

    Briefly identify the distinctive capabilities:

    • Exact structured numerical data, including irrational Powers, structured Quotients, and Complex values with independently typed components.
    • Portable typed Arrays alongside recursively structured collections.
    • Deterministic binary identity and SHA-256 fingerprinting.
    • Human-readable input and identity-preserving YAML and HDF5 representations.
    • External-resource references with deferred retrieval and integrity checks.

    Describe the Python package as the reference implementation of a language-independent specification. Avoid an API inventory or encoding tutorial in the summary.

    2. Statement of need

    Research problem and audience

    Address developers of long-lived computational science and engineering software, especially workflows that combine exact numerical structure with large machine Arrays.

    Explain the practical requirements using a concrete scientific object: a crystal structure or symmetry calculation containing lattice Arrays, fractional coordinates, exact complex phase factors, parameters, and externally stored numerical results.

    Such an object may need to survive storage changes, support reproducible identification, and move between implementations while retaining distinctions that matter to the application.

    Scientific example

    Use a structured complex phase factor as the central numerical example:

    complex(1/2, 1/2 * sqrt(3))

    This preserves the exact real and irrational imaginary components instead of immediately replacing both with floating-point approximations. Discuss why this is useful for crystallographic or symmetry data, alongside ordinary floating-point Arrays required by numerical calculations.

    Mention that DataCanon preserves type and constituent structure without mathematical simplification. Detailed normalization edge cases belong in the specifications rather than the motivation.

    Practical outcome

    Explain what the package enables: identity-preserving disk round trips, format transfers, and stable fingerprints of scientifically meaningful data. If a code fragment is needed, use one short persistence example; leave a full walkthrough in Getting Started.

    3. State of the field

    Compare against existing software and standards using primary documentation and appropriate software citations. This section requires a focused literature review before it becomes manuscript prose.

    Candidate comparison families include JSON canonicalization, deterministic CBOR, schema-driven serialization, YAML tooling, HDF5, and scientific data containers used by the intended audience. Select the closest alternatives rather than cataloguing every serialization format.

    Evaluate the distinctions that motivate DataCanon:

    ConcernQuestion for the comparison
    IdentityWhat equality relation and canonical encoding are provided?
    Scientific typesHow are structured exact numbers and typed Arrays represented?
    CollectionsAre ordered and unordered structures distinguished?
    PersistenceCan storage layout change while retaining the same identity?
    External dataHow are payload metadata, content verification, and retrieval separated?
    InteroperabilityWhat agreement is required across implementations?

    Give a concrete reason for developing DataCanon rather than extending a particular existing package. The proposed contribution is the combination of an explicit scientific data model, canonical identity, and multiple faithful representations. Existing formats may provide related capabilities or support extensions; comparisons must establish the relevant differences rather than claiming that canonicalization or portability is unique to DataCanon.

    Explain that DataCanon uses mature facilities such as NumPy and HDF5 instead of replacing their numerical and storage infrastructure.

    4. Software design

    Organize this section around decisions and their consequences for scientific workflows. Keep low-level byte tables in the specifications.

    Identity is separate from representation

    Define DCT and DCI briefly. Equality is specified by types and constituents; canonical encoding represents that equality injectively:

    x = y  if and only if  E(x) = E(y)

    Fingerprinting is:

    F(x) = SHA-256(E(x))

    Shorthand formatting does not determine identity. Distinguish exact canonical byte equality from digest comparisons, which rely on collision resistance.

    Scientific types and machine Arrays

    Version 1 defines 22 DCTs: seven primitive types, three atomic types, and twelve composite types. Highlight composable numerical structures, Complex, Record, Multiset, Bytes, Array, and external references rather than explaining every type in the paper.

    Numerical DCIs are Integer, Float, Fraction, Sum, Product, Power, and Quotient. This is a category for constituent restrictions, not an additional DCT. Type membership makes no assertion about mathematical evaluability.

    Explain the composition rule with a concrete example. Fraction’s prescribed integers are direct information. A Complex component or Power base is a DCI, whose individual DCT and recursive structure matter. Encoding reuses shared payload rules for direct fields and complete DCI encodings for variable-type constituents.

    Arrays retain portable type, shape, and element identity. Their elements are machine values, not individually tagged DCIs. The 14 portable Array types support efficient numerical containers; canonical elements use logical C order and prescribed big-endian multibyte representations, independently of native strides or layout. Nested Lists remain available for individually typed constituent data.

    Distinguish the fully specified core Array identity from the draft Shorthand rules for inference and conversion, whose NumPy reference behavior still needs finalization.

    Order belongs to the data model

    Mapping entry order participates in identity; UnorderedMapping entry order does not. Likewise, Lists and Tuples are ordered, while Sets are unordered. Multiset retains repeated members; Sum and Product similarly retain Numerical operand multiplicity and nesting. Canonical binary encoding sorts Set and Multiset members, Sum and Product operands, and UnorderedMapping keys by their complete canonical encodings. That encoding order is not a numerical comparison or a mandated text-rendering order.

    Text and conventional-type conversion

    One strict Shorthand grammar accepts explicit constructors and shorter forms. Longhand uses constructors for structured values and ordinary literals for Null, Boolean, Integer, Float, and String. The boundary is syntactic rather than the Core type classification: primitive Fraction still uses fraction(...). Bytes and Array elements retain their prescribed syntax. For example, sum(1, 1.0, fraction(1, 2)) is longhand without additional literal wrappers. The renderer’s longhand flag is independent of its layout styles; constructor fallbacks preserve nested structure in the default rendering.

    The Python binding separates delimiter layout, column alignment, structural indentation, and padding beside shared delimiters. Layout can be standard, semi-compact, compact, or inline, globally or per type; alignment can be disabled or set left/right. Per-type custom_layout overrides leave unspecified types using the global layout. Inline parents force all descendants onto one line. Padding controls same-line gaps, while indentation controls nested blocks on new lines. Sets and other constructor forms use the same contracts. Formatting choices preserve DCI identity.

    Define conventional types as types used directly for data and computation in a programming language, including built-in, library-provided, and user-defined types. The conversion interface constructs instances of conventional types from DCIs and constructs DCIs from supported conventional objects. A ListDC object and a conventional list object are both Python objects, but their types and equality contracts differ.

    Existing conventional types include list, Fraction, and NumPy arrays. The reference implementation supplies new conventional types such as Power, Sum, and Multiset where suitable types are missing. Arithmetic belongs to the numerical conventional types, not to the DCT identity rules. Conventional Sum and Product simplify matching terms and factors; explicit float() and int() request numerical results. Conversion through conventional objects need not preserve an arbitrary DCI’s identity.

    Present conventional arithmetic as an optional companion interface in the paper, without introducing a separately named arithmetic facility. The seventh specification, Conventional Types, defines common behavior for independent implementations, with conformance declared per type. Core does not require that support. Link the Conventional Types guide for worked examples and the companion specification for its behavioral requirements and comparison limits.

    Contained and external payloads

    Bytes stores an opaque byte sequence directly in the DCI. A Record can hold its interpretation metadata. This permits a canonical binary file to contain both structured scientific data and binary payloads without companion files. External references serve the distinct purpose described below.

    External payloads and persistence

    ExternalFile and ExternalArray retain relative paths and content digests as semantic metadata. ExternalArray also carries portable type and shape. External bytes are not needed to decode or fingerprint their metadata.

    Source location, cached bytes, and retrieval state are nonsemantic. Retrieval verifies digests and, for ExternalArray, element-stream validity. Complete packages preserve those references while placing payloads in directory-backed storage or embedding them in HDF5.

    Seven specifications and the Python implementation

    Summarize the specification boundaries:

    SpecificationResponsibility
    CoreDCTs, equality, canonical bytes, and fingerprints
    ShorthandStrict text parsing and identity-preserving rendering
    Shorthand PreprocessingOptional compact Lists, substitutions, and explicit eval(...)
    YAML InterchangeNative YAML conversion and the $ convention
    HDF5Portable object layout, numerical datasets, and embedded payloads
    PersistenceFormat selection, resource namespaces, verification, and transfer
    Conventional TypesOptional conventional construction, arithmetic, comparison, collections, and conversion contracts

    Connect the contracts to explicit conversion, encoding/decoding, parser/renderer, and persistence boundaries. The DCTs and DCI equality are language-independent. The optional Conventional Types companion specifies a common behavioral foundation. Language bindings document their supported types, interfaces, additional simplifications, and conversion choices. Python classes are examples of a binding rather than normative DCT definitions.

    Core does not perform computation. Optional preprocessing performs explicitly requested arithmetic before strict parsing; it does not alter DCT identity.

    5. Research impact statement

    Build this section from specific evidence available at submission time. Distinguish actual use from proposed applications.

    Possible evidence to collect includes:

    • A documented Principia Materia integration showing which scientific objects use DataCanon and what workflow it supports.
    • Reproducible crystallographic or symmetry examples using exact structured Complex values and typed Arrays.
    • Verified format transfers preserving canonical bytes and fingerprints.
    • Benchmarks for representative numerical workloads, if performance is a material reason to adopt the package.
    • Independent users, integrations, or publications, if available.

    The repository tree shows tests covering conversion, canonical encoding and vectors, parsing/rendering, YAML, HDF5, and external sources. Report test results and fixtures only after running and inspecting them; filenames alone are not validation evidence.

    If Julia conformance is completed, include independently generated matching canonical bytes and fingerprints, all portable Array types, and bidirectional HDF5 fixtures. Text layout and HDF5 file bytes need not match. Report completed coverage and remaining limitations explicitly.

    6. AI usage disclosure

    Prepare an accurate account of AI assistance with software development, documentation, or manuscript preparation, together with the human review and verification performed. This documentation and outline have received AI assistance. The implementation, tests, specifications, and documentation have also received AI assistance during this redesign. Record the reviewed scope and the actual human checks performed before preparing submission text.

    Record the tools and available version information when preparing the submission. Do not describe syntax-only checks as execution, interoperability validation, or scientific verification.

    7. Acknowledgements

    Identify contributors, institutional support, and funding actually associated with the software. Obtain the correct grant identifiers and attribution before submission.

    8. References

    Prepare software and primary-source citations for the closest alternatives, the numerical/storage facilities discussed, and scientific applications used as evidence. Link the versioned DataCanon specifications and archive the software release associated with the paper.

    Version 1 draft revisions

    The numerical redesign replaces Coefficient with Sum, Product, Power, and Quotient. Multiset and Bytes are now first-class DCTs. Fixed integer and Unicode fields use direct payload encodings; affected earlier draft bytes and fingerprints are incompatible with the current encoding.

    Use the finalized Version 1 encodings for publication fixtures. Do not mix results from incompatible draft revisions. Tests should cover the full numerical structure, both longhand and shorter text forms, byte payloads, multisets, and transfers preserving the current canonical bytes.

    Supporting material and remaining work

    The documentation should provide the material omitted from the short paper: full type definitions, byte encodings, fixed conformance vectors, API signatures, numerical Python behavior, longhand rendering, preprocessing details, and persistence examples.

    Before finalizing the manuscript, resolve or clearly delimit the portability items already recorded in the seven drafts, especially NumPy/PyYAML reference behavior, preprocessing numerical semantics, and HDF5 datatype validation. Confirm the package’s license, release, installation instructions, tests, contribution guidance, and cited scientific evidence against the actual repository. The checklist identifies items to inspect, not claims that they are currently missing.

    A longer technical treatment could develop the full model and conformance results separately. The JOSS paper should stay centered on the research software, its design choices, and demonstrated usefulness.
