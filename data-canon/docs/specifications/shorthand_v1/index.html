    Shorthand

    DataCanon Shorthand — Version 1 Draft

    Status: Draft for independent implementation review
    Depends on: DataCanon Core Version 1
    Scope: Strict Shorthand parsing and identity-preserving rendering
    Out of scope: Optional Shorthand preprocessing, YAML interchange, HDF5, and persistence conventions

    Introduction

    DataCanon Shorthand is a human-readable textual representation of DataCanon Instances (DCIs). It provides notation for all 17 DataCanon Types (DCTs) defined by DataCanon Core Version 1.

    Shorthand does not define DCI identity. The core specification defines DCTs, equality, canonical binary encoding, and fingerprinting. A Shorthand document represents exactly one DCI; its whitespace and textual layout do not participate in that DCI’s identity.

    A conforming Shorthand parser MUST recover the DCI specified by a valid Shorthand document. A conforming Shorthand renderer MUST produce valid Shorthand that a conforming parser recovers as a DCI equal to the original.

    Shorthand is not a canonical textual encoding. Multiple texts may represent the same DCI, and no particular rendering layout is required.

    Conformance and terminology

    The terms MUST, MUST NOT, SHOULD, and MAY indicate requirements and recommendations for implementations of this specification.

    The definitions, invariants, and equality relations of DataCanon Core Version 1 take precedence over any convenience afforded by Shorthand syntax. A syntactically well-formed expression that violates a DCT invariant is invalid Shorthand.

    A conforming strict parser MUST:

    • parse exactly one complete DCI and reject unexpected trailing input;
    • interpret the constructs specified here according to their defined DCTs;
    • preserve constituent identity, including unreduced Fractions and floating-point signed zero;
    • reject invalid DCT constituents and malformed syntax; and
    • operate without performing substitutions, mathematical evaluation, or application-specific transformations.

    A conforming renderer MUST preserve DCI equality across a strict render–parse round trip. It MAY choose whitespace, indentation, line breaks, and other identity-preserving layout conventions.

    The separately specified Shorthand preprocessor MAY be applied before strict parsing. It is not part of the strict grammar.

    Lexical rules

    Input and whitespace

    Shorthand is Unicode text. Strings may contain Unicode scalar values as defined by DataCanon Core Version 1.

    Outside quoted strings, the recognized whitespace characters are the ASCII space (U+0020), horizontal tab (U+0009), carriage return (U+000D), and line feed (U+000A). Whitespace may appear between syntactic tokens except where this specification explicitly requires adjacent characters.

    Strict Shorthand does not define comments. An empty or whitespace-only document is invalid.

    Digits and identifiers

    A digit is one of the ASCII characters 0 through 9.

    An identifier begins with an ASCII letter (A–Z, a–z) or underscore (_), followed by zero or more ASCII letters, digits, or underscores.

    The strict grammar recognizes only the identifiers explicitly assigned meaning below. Arbitrary identifiers are not variables and MUST be rejected in strict parsing.

    Identifiers and keywords are case-sensitive. In particular, true, false, and null are lowercase.

    Strings

    A String literal is delimited by double quotation marks ("). Its contents are a sequence of Unicode scalar values, optionally using the following escapes:

    Source charactersDecoded character
    \"quotation mark
    \\backslash
    \nline feed
    \rcarriage return
    \thorizontal tab

    No other backslash escapes are defined. A backslash followed by any other character MUST be rejected. Literal Unicode characters, including literal line breaks, may appear inside a quoted string, provided the decoded result is a valid DataCanon String. No Unicode normalization occurs.

    A renderer MUST escape quotation marks and backslashes so that they cannot terminate or alter a String literal; it MAY escape the three supported control characters above.

    Numerical literals

    An integer literal consists of an optional leading - followed immediately by one or more ASCII digits. It denotes an arbitrary-precision mathematical integer in decimal notation. A leading + is not supported.

    A floating-point literal consists of an optional leading -, a nonempty sequence of ASCII digits, and at least one of:

    • a decimal point followed by one or more ASCII digits; or
    • an exponent introduced by e or E, followed by an optional + or - and one or more ASCII digits.

    A floating-point literal may have both a decimal part and an exponent, such as 1.25e-3. The scalar syntax does not require support for a trailing decimal point without following digits (for example, 1.). Array element syntax has a separate allowance for that form.

    A floating-point literal denotes the finite IEEE-754 binary64 value obtained by correctly rounding its decimal value. The parser MUST reject values that cannot produce a valid finite Float DCI. Positive and negative zero are distinct.

    A Fraction literal consists of an integer literal, /, and one or more ASCII digits denoting a positive denominator, with no intervening whitespace. The numerator and denominator are preserved exactly; no reduction occurs.

    Examples:

    TextDCTInterpretation
    42Integerinteger 42
    -0Integerinteger 0
    -0.0Floatnegative binary64 zero
    1e3Floatbinary64 1000.0
    2/4Fractionnumerator 2, denominator 4

    Strict Shorthand constructs

    Primitive DCTs

    DCTSyntaxExample
    Nullnullnull
    Booleantrue or falsetrue

    Fraction

    A Fraction is written as a Fraction literal, for example 1/3 or 2/4. Its denominator MUST be positive. It is distinct from an Integer or Float with the same mathematical value.

    Coefficient

    A Coefficient represents the five constituents (scale, numerator, denominator, radicand, offset) defined in the core specification. Shorthand uses a restricted factor notation; this is not general arithmetic.

    Permitted factors are:

    • a floating-point factor supplying the scale;
    • an integer or Fraction factor supplying the rational numerator and denominator; and
    • sqrt( positive integer ) supplying the radicand.

    Factors are separated by *, with optional whitespace around the operator. At most one factor of each kind is permitted. Omitted factors have the core DCT’s identity defaults: scale=1.0, numerator=1, denominator=1, and radicand=1.

    A bare sqrt(3) denotes a Coefficient, not a function call or a computed floating-point value.

    When no sqrt(...) factor is present, a terminal * 1 can identify the expression as a Coefficient rather than as an ordinary numeric DCI. For example, 1/2 * 1 is a Coefficient, while 1/2 is a Fraction. The terminal identity factor is not a second rational factor and MUST terminate the multiplicative expression.

    An optional offset is written as + followed by a floating-point literal, including a negative floating-point literal such as -0.225. The offset defaults to positive 0.0 when omitted. An offset expression identifies a Coefficient even without * or sqrt(...).

    Examples:

    TextRelevant constituents
    sqrt(3)radicand 3
    2 * sqrt(3)numerator 2, radicand 3
    1.89 * 1/2 * sqrt(3)scale 1.89, numerator 1, denominator 2, radicand 3
    1/2 * 1numerator 1, denominator 2, radicand 1
    1 + 0.225numerator 1, radicand 1, offset 0.225
    1/2 * sqrt(3) + -0.225offset -0.225
    1 + -0.0negative-zero offset

    Expressions such as 2 * 3, 1/2 * 2/3, sqrt(2) * sqrt(3), and 1/2 + 1/3 are invalid strict Shorthand. No simplification or computation is performed.

    Complex

    A Complex is written:

    complex(real, imaginary)

    Each component MUST parse to an Integer, Float, Fraction, or Coefficient DCI. The two components retain their DCTs and their individual identities.

    Example:

    complex(1/2, 1/2 * sqrt(3))

    This notation is distinct from the special complex-number syntax used inside Arrays.

    List and Tuple

    A List uses square brackets and a Tuple uses parentheses. Elements are arbitrary DCIs separated by commas. Both may be empty and may have an optional trailing comma.

    []
[1, "x", 2/4]
(1, 2)
(1)
()

    A single-element Tuple is (1); no trailing comma is required. List and Tuple remain distinct DCTs regardless of their contents.

    Set and Mapping

    Curly braces denote a nonempty Set or a Mapping, distinguished by the presence of : following the first parsed value.

    {1, 2, 3}
{"a": 1, "b": 2}
{}

    {} is the empty Mapping. The empty Set is spelled emptyset.

    Set members are arbitrary DCIs separated by commas. They MUST be pairwise distinct under DCI equality. Set member order is not semantic. The current strict grammar does not admit a trailing comma in a Set.

    A Mapping consists of comma-separated key: value entries. Keys and values are arbitrary DCIs, and keys MUST be pairwise distinct under DCI equality. Entry order is semantic. A Mapping may have an optional trailing comma.

    UnorderedMapping

    An UnorderedMapping is written:

    umapping("b": 2, "a": 1)
umapping()

    It follows Mapping entry syntax and uniqueness requirements, but entry order is not semantic. An optional trailing comma is permitted.

    Record

    A Record is written with a quoted name followed by zero or more quoted field names and DCI values:

    record("Point", "x": 1.0, "y": 2.0)
record("Empty")

    The Record name and each field name are DataCanon Strings. Field names MUST be distinct. Field order and the Record name participate in DCI identity. A trailing comma after the Record name or final field is permitted.

    Record names and field names need not be valid Shorthand identifiers because they are quoted Strings.

    Arrays

    Array construct

    An Array is written:

    array(DATA)
array(DATA, dtype="TYPE")
array(DATA, shape=(DIMENSIONS))
array(DATA, dtype="TYPE", shape=(DIMENSIONS))

    The dtype and shape options may occur in either order, at most once each. An optional comma before the closing ) is permitted.

    DATA is either a single Array scalar (rank zero) or a nested bracketed collection of Array scalar elements. Array elements are not DCIs. A nested Array body is not a DataCanon List.

    Examples:

    array(1.0)
array([1, 2, 3])
array([[1.0, 2.0], [3.0, 4.0]])
array([1.0, -0.0], dtype="float32")
array([], dtype="float64", shape=(0, 3))

    The bracketed numerical body uses comma-separated entries and rectangular nesting. The current strict parser does not permit a trailing comma inside a bracketed Array body.

    Array scalar syntax

    Array scalar elements may be true, false, real numeric literals, or complex numeric literals of the form:

    REAL+MAGNITUDEj
REAL-MAGNITUDEj

    REAL and MAGNITUDE use Array numeric syntax. The real part may be negative; the imaginary magnitude is unsigned. No whitespace is permitted within the complex literal. Exponents are permitted in either component, and the decimal point in an Array numeric literal may have no following digit (1.).

    Examples:

    array([true, false])
array([1., 2.5])
array([1.0+2.0j, 3.0-4.0j])
array([1e-3+2e4j, -3e2-4e-1j])

    1.0+2.0j is not a valid top-level Complex DCI expression.

    Portable Array types

    The resulting Array MUST have one of the 14 portable Array types defined by DataCanon Core Version 1:

    bool, int8, int16, int32, int64, uint8, uint16, uint32, uint64, float16, float32, float64, complex64, and complex128.

    A dtype option is a quoted type name. The portable type names above are the interoperable spelling; the Python reference parser also accepts dtype aliases recognized by NumPy when they produce a portable type. Whether to standardize aliases beyond the portable names is open for Version 1 finalization.

    Inference and explicit conversion

    When dtype is omitted, the reference behavior is NumPy’s array construction from the parsed Array scalar values. When shape is omitted, the reference behavior is the shape inferred from that construction.

    When dtype is present, the reference behavior is NumPy Array construction with that dtype. NumPy’s conversion behavior, including any permitted rounding or lossy conversion, is intentionally retained. Shorthand does not impose a separate losslessness rule on explicit dtype conversion. The final Array MUST nevertheless satisfy the portable Array DCT’s invariants, including finiteness of floating-point and complex elements.

    When shape is present, the constructed Array is reshaped using NumPy-compatible reshape semantics; the requested shape MUST be valid, have nonnegative dimensions, and preserve the element count.

    Reference-version item pending: Before this draft becomes a final cross-language conformance standard, the NumPy reference version MUST be fixed. Julia and other implementations need only reproduce the resulting DCI, not use NumPy internally. The detailed inference and conversion algorithm is deliberately not reproduced in this draft.

    Array identity and rendering

    Array type, shape, and the exact portable element values participate in identity. Renderers MUST include dtype and shape annotations whenever omitting them would cause a conforming parser to infer a different DCI.

    A renderer MUST preserve the bit identities of floating-point Array elements, including positive and negative zero, and the corresponding components of complex Array elements.

    The canonical element byte stream and canonical Array encoding are defined only by DataCanon Core Version 1, not by Shorthand formatting.

    External resources

    Relative paths

    Shorthand writes a DataCanon relative path as one quoted String whose components are joined by the ASCII slash (/). The parser splits that String on / to reconstruct the abstract DataCanon relative path.

    Each component MUST satisfy the relative-path invariants of DataCanon Core Version 1. In particular, empty components, . and .., and components containing backslashes are invalid.

    Parsing an external DCI does not access its external resource.

    ExternalFile

    external_file("inputs/INCAR", "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef")

    The first argument is a relative path String. The second is a quoted hexadecimal SHA-256 digest decoding to exactly 32 bytes. A renderer SHOULD use 64 lowercase hexadecimal characters. A conforming parser MUST accept that spelling and MAY accept uppercase hexadecimal digits. Whitespace within a hexadecimal digest String is not part of the portable normative spelling.

    ExternalArray

    external_array("data/forces.bin", "float64", (100, 3), "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef")

    The arguments, in order, are a relative path String, a portable Array type String, a Tuple of nonnegative Integer dimensions, and a quoted SHA-256 digest decoding to exactly 32 bytes.

    The external byte stream is defined by DataCanon Core Version 1. Shorthand carries the path, Array type, shape, and digest, but not the external contents.

    Rendering requirements

    A conforming renderer MUST satisfy, for every valid DCI x:

    parse_shorthand(render_shorthand(x)) = x

    Here equality means DCI equality as defined by DataCanon Core Version 1. The equation describes the behavior of conforming parser and renderer operations, not mandated function names in other programming languages.

    Renderers MAY choose their own whitespace, indentation, line breaking, column alignment, and compactness policies. The Python reference implementation’s standard, aligned, and aligned-compact styles are not distinct dialects and are not normative style names.

    Renderers MUST NOT normalize Fractions or Coefficients mathematically, erase Float signed zero, reorder ordered collections, or change any other constituent that participates in DCI identity.

    A renderer of an unordered collection MAY choose any entry/member order accepted by the strict parser. The canonical ordering of the binary encoding does not impose a textual ordering requirement.

    Invalid input and error handling

    A conforming parser MUST reject malformed syntax, unsupported identifiers, invalid numeric values, invalid escape sequences, duplicate keys or fields, invalid Array shapes or types, invalid external paths or digests, and input remaining after a complete DCI has been parsed.

    An implementation MAY use its own error types and diagnostics. No specific error-message text is required by this specification.

    Implementations MAY impose resource limits on text size, nesting depth, Array allocation, or integer magnitude. Such limits are implementation constraints and do not change DCI identity.

    Relationship to other DataCanon specifications

    • DataCanon Core V1 defines the DCTs, equality, canonical encoding, and fingerprinting.
    • Shorthand Preprocessing V1 (separate document) will define compact List notation, general substitutions, and restricted scalar eval(...) transformations before strict parsing.
    • YAML Interchange V1 (separate document) may embed strict Shorthand using the DC> convention.
    • HDF5 V1 and Persistence V1 (separate documents) will define storage and external-resource conventions.

    Neither the preprocessor nor a persistence mechanism alters the strict Shorthand grammar defined here.

    Appendix B — Outstanding Version 1 finalization items

    These items are deliberately recorded rather than silently resolved by assumptions about other languages:

    1. Pin the NumPy reference version governing Array inference, dtype conversion, and shape construction. This is the principal remaining cross-language portability dependency.
    2. Decide whether NumPy dtype aliases beyond the 14 portable Array type names are normative input or only permissive Python extensions.
    3. Confirm the exact treatment of optional noncanonical hexadecimal digest spellings, if interoperability with hand-authored external references warrants it.
    4. Publish cross-implementation vectors pairing Shorthand input with canonical Core V1 bytes, especially for Arrays, Coefficients, and external references.

    None of these items changes the 17 core DCT definitions or the Core V1 canonical byte encoding.
