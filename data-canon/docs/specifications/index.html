    Specification

    Version 1 Draft

    Introduction

    DataCanon (DC) is a formal language for representing structured scientific data.

    Its primary purpose is to assign a deterministic, language-independent semantic identity to scientific data. DataCanon Values may be fingerprinted or stored using alternative persistence mechanisms while preserving their identity.

    DataCanon defines a set of semantic types and a canonical textual encoding for each instance of those types.

    The Python reference implementation uses the Data Skeleton, an immutable intermediate representation, to implement DataCanon parsing, rendering, conversion, fingerprinting, and persistence.

    DataCanon is intended for scientific software whose data must remain stable, portable, reproducible, and meaningful over years or decades of development.

    Implementations may provide additional interfaces for human-oriented input, rendering, or interchange, provided those interfaces preserve the underlying DataCanon semantics.

    Goals

    DataCanon is designed to solve four practical engineering problems.

    • deterministic rendering
    • deterministic fingerprinting
    • language-independent interchange
    • long-term persistence

    These goals support scientific software whose data must remain robust over the lifetime of a project rather than the lifetime of a particular programming language or serialization format.

    Non-Goals

    DataCanon intentionally does not provide

    • symbolic algebra
    • computation
    • variables
    • user-defined functions
    • expression evaluation
    • units
    • dimensional analysis

    DataCanon represents structured data.

    It does not manipulate that data or define mathematical operations between values.

    DataCanon canonicalizes representation, not mathematics. Mathematical relationships between distinct DataCanon Values are outside the DataCanon specification.

    The * and + characters appearing in Coefficient syntax do not define general arithmetic operators. They are structural components of that semantic type.

    Terminology

    The following terms are used throughout this specification.

    DataCanon semantic type A data type defined by the DataCanon specification. Each DCST defines the information constituting its instances, the invariants those instances must satisfy, the equality relation between its instances, and their canonical representation. Composite DCSTs may recursively contain instances of other DCSTs.

    DataCanon Semantic Instance (DCSI) An instance of exactly one DCST. DCSI equality is defined by the corresponding DCST and is independent of any implementation-language representation.

    DataCanon Value (DCV) Canonical DataCanon text encoding exactly one DCSI.

    DataCanon Source (DCS) Text intended as input to a DataCanon parser.

    A DCS may contain textual freedoms permitted by the parser, such as noncanonical whitespace or other accepted noncanonical syntax.

    Valid DataCanon Source (valid DCS) A DCS accepted by a conforming DataCanon parser.

    For example,

    [1,2,3]

    and

    [ 1, 2, 3 ]

    are distinct valid DCSs. Parsing and rendering either produces the same DCV:

    [1, 2, 3]

    A DCV is itself a valid DCS.

    Parsing The interpretation of a valid DCS according to the DataCanon grammar and semantic types.

    Parsing determines the instances of DataCanon semantic types encoded by the source while discarding textual distinctions that do not participate in their DCVs.

    Rendering The production of the unique DCV corresponding to an instance of a DataCanon semantic type.

    Thus, parsing followed by rendering canonicalizes valid DCS:

    Valid DCS  →  parsing  →  rendering  →  DCV

    For a DCV, this operation is idempotent:

    render(parse(DCV)) = DCV

    Design Principles

    DataCanon satisfies the following fundamental properties.

    Deterministic

    Every instance of a DataCanon semantic type has exactly one DataCanon Value (DCV).

    Rendering a given instance therefore always produces the same DCV.

    Lossless

    Parsing and rendering preserve the instance encoded by valid DataCanon source.

    A DCV is a fixed point of parsing and rendering:

    render(parse(DCV)) = DCV

    Language Independent

    The DataCanon specification is independent of Python or any other implementation language.

    Different implementations may use different internal representations while producing identical DCVs.

    Stable

    The DataCanon language evolves independently of any persistence mechanism.

    An instance of a DataCanon semantic type may be encoded as a DCV or preserved using an alternative persistence mechanism such as HDF5 without changing its DataCanon identity.

    Minimal

    The language favors simple, deterministic rules over expressive but ambiguous alternatives.

    DataCanon defines only the structure and canonical representation necessary to identify its semantic types. It does not define general computation or mathematical simplification.

    Primitive Types

    Integer

    The Integer DCST represents the mathematical integers (\mathbb{Z}).

    An Integer DCSI consists of exactly one mathematical integer. Integer has unlimited precision.

    Two Integer DCSIs are equal if and only if they represent the same mathematical integer.

    The canonical representation of an Integer is its base-10 representation, preceded by - if the value is negative.

    Float

    The Float DCST represents finite IEEE-754 binary64 values.

    A Float DCSI consists of exactly one finite IEEE-754 binary64 value, including its sign. Positive and negative zero are therefore distinct Float DCSIs.

    Two Float DCSIs are equal if and only if their IEEE-754 binary64 bit representations are identical.

    NaN and positive and negative infinity are not Float DCSIs in Version 1.

    Floating-point values are inherently approximate. Applications requiring an explicitly rational representation should use a suitable exact DataCanon semantic type.

    The canonical representation of a Float is a decimal floating-point literal that uniquely identifies its binary64 value according to the canonical rendering rules.

    String

    The String DCST represents finite sequences of Unicode scalar values.

    A String DCSI consists of exactly one such sequence.

    Two String DCSIs are equal if and only if they contain identical sequences of Unicode scalar values.

    DataCanon performs no Unicode normalization. Strings that are visually identical but consist of different sequences of Unicode scalar values are therefore distinct String DCSIs.

    String literals are enclosed by double quotation marks.

    Single-quoted strings are not part of Version 1.

    Boolean

    The Boolean DCST contains exactly two DCSIs, canonically represented as

    true
false

    Two Boolean DCSIs are equal if and only if they represent the same Boolean value.

    Boolean is semantically distinct from Integer. In particular, true and 1 are instances of different DCSTs and are not equal.

    Null

    The Null DCST contains exactly one DCSI.

    Its canonical representation is

    null

    All Null DCSIs are therefore equal.

    Atomic Types

    Atomic semantic types represent values that are conceptually indivisible despite having internal structure.

    They render on a single line.

    Fraction

    The Fraction DCST represents a structured ratio of two mathematical integers.

    A Fraction DCSI consists of

    • an Integer numerator, and
    • a positive Integer denominator.

    The denominator MUST be nonzero and positive.

    Two Fraction DCSIs are equal if and only if their numerators are equal and their denominators are equal.

    Thus, Fraction identity is structural rather than mathematical. For example,

    1/2

    and

    2/4

    represent distinct Fraction DCSIs even though they denote the same rational number mathematically.

    DataCanon does not reduce, normalize, or otherwise mathematically simplify Fractions.

    The canonical representation of a Fraction is

    numerator/denominator

    with the numerator and denominator rendered according to the canonical Integer rules.

    Fractions are semantic values, not arithmetic expressions. The / character is part of Fraction syntax and does not define a general division operator.

    Coefficient

    The Coefficient DCST represents a structured numerical decomposition consisting of a multiplicative term and an additive floating-point offset.

    A Coefficient DCSI consists of five constituents:

    • a Float scale,
    • an Integer numerator,
    • a positive Integer denominator,
    • a positive Integer radicand,
    • a Float offset.

    The constituents have the identity values

    scale       = 1.0
numerator   = 1
denominator = 1
radicand    = 1
offset      = 0.0

    The denominator and radicand MUST be positive.

    The scale and offset MUST be finite Float DCSIs. When the offset is zero, it MUST be positive zero. Negative zero is not permitted as a zero Coefficient offset.

    Two Coefficient DCSIs are equal if and only if all five corresponding constituents are equal according to their respective DCST equality rules.

    Thus, Coefficient identity is structural rather than mathematical. DataCanon does not reduce, simplify, or otherwise mathematically transform the constituents of a Coefficient.

    For example,

    sqrt(12)

    and

    2 * sqrt(3)

    represent distinct Coefficient DCSIs.

    Likewise, distinct rational structures remain distinct. No common factors are cancelled between the numerator and denominator.

    Canonical Representation

    A Coefficient has the general structural form

    scale * numerator/denominator * sqrt(radicand) + offset

    The multiplicative term contains the scale, rational factor, and square-root factor represented by the corresponding Coefficient constituents.

    Canonical rendering emits multiplicative factors in the order

    1. floating-point scale,
    2. rational factor,
    3. square-root factor,

    followed by the additive offset when the offset is nonzero.

    Identity factors are omitted whenever their omission does not make the Coefficient indistinguishable from another DCST.

    For example,

    sqrt(2)

2 * sqrt(2)

1/2 * sqrt(3)

1.89 * 1

1.89 * sqrt(3)

1.89 * 1/2 * sqrt(3)

1/4 + 0.199

3/4 + -0.199

sqrt(2) + 0.225

1.89 * 1/2 * sqrt(3) + 0.225

    are Coefficient representations.

    The square-root factor is omitted when the radicand is 1.

    Thus,

    sqrt(3)

    already identifies the Coefficient DCST and requires no additional identity factor.

    In contrast,

    1/2

    is not a Coefficient, while

    1/2 * 1

    is a Coefficient whose radicand is 1.

    Similarly,

    1.89

    is a Float, while

    1.89 * 1

    is a Coefficient.

    When the offset is nonzero, the + syntax itself identifies the Coefficient DCST. Therefore,

    1/2 + 0.225

    requires no multiplicative identity factor.

    The offset is omitted when it is positive zero.

    Valid Source

    A parser MAY accept multiplicative factors in any order, provided that the source unambiguously determines the five constituents of the Coefficient DCSI.

    A Coefficient may contain at most one factor of each multiplicative kind and at most one additive offset.

    The offset must be a Float literal. Thus,

    1/2 + 0.225

    is valid Coefficient syntax, while

    1/2 + 1/3

    is not.

    Coefficients are not arithmetic expressions.

    The *, +, and sqrt(...) syntax appearing in a Coefficient describes its structure. These constructs do not define general multiplication, addition, or square-root operations in DataCanon.

    Complex

    The Complex DCST represents a structured complex number consisting of a real component and an imaginary component.

    A Complex DCSI consists of

    • a real component, and
    • an imaginary component,

    each of which MUST be a DCSI of one of the following real-valued numerical DCSTs:

    • Integer,
    • Float,
    • Fraction,
    • Coefficient.

    Two Complex DCSIs are equal if and only if their real components are equal and their imaginary components are equal according to their respective DCST equality rules.

    The DCST of each component therefore participates in Complex identity.

    For example,

    complex(1, 2)

    and

    complex(1.0, 2.0)

    represent distinct Complex DCSIs because Integer and Float are distinct DCSTs.

    Likewise,

    complex(1/2, 1/2 * sqrt(3))

    preserves the Fraction and Coefficient structures of its components exactly.

    DataCanon does not convert Complex components to floating-point values or otherwise mathematically simplify them.

    Canonical Representation

    The canonical representation of a Complex DCSI is

    complex(real, imaginary)

    where real and imaginary are the DCVs of the corresponding component DCSIs.

    For example,

    complex(1, 2)

complex(1.0, -3.5)

complex(1/2, 3/4)

complex(1/2, 1/2 * sqrt(3))

    are Complex representations.

    Because the component DCSTs participate in Complex identity, canonical rendering preserves their distinctions. Integer components are not converted to Float components, Fractions are not reduced or converted to floating point, and Coefficients retain their encoded structure.

    Complex values are not arithmetic expressions.

    The complex(...) syntax constructs a Complex DCSI from two real-valued numerical DCSIs. It does not define complex arithmetic or mathematical evaluation in DataCanon.

    Composite Types

    Composite DCSTs contain collections of other DCSIs.

    Their identity is determined by their constituent DCSIs according to the structure and equality rules defined by each composite DCST.

    List

    The List DCST represents a finite ordered sequence of DCSIs.

    A List DCSI consists of zero or more DCSIs in a defined order.

    Two List DCSIs are equal if and only if

    • they contain the same number of items, and
    • corresponding items are equal according to their respective DCST equality rules.

    Thus, item order participates in List identity.

    For example,

    [1, 2]

    and

    [2, 1]

    represent distinct List DCSIs.

    The canonical representation of a List is

    [item1, item2, ...]

    where each item is represented by its DCV.

    An empty List is represented as

    []

    Lists may recursively contain DCSIs of any DCST, including other composite DCSTs.

    For example,

    [1, 1/2, [2, 3], (4, 5)]

    is a List containing an Integer, a Fraction, another List, and a Tuple.

    Tuple

    The Tuple DCST represents a finite ordered sequence of DCSIs.

    A Tuple DCSI consists of zero or more DCSIs in a defined order.

    Two Tuple DCSIs are equal if and only if

    • they contain the same number of items, and
    • corresponding items are equal according to their respective DCST equality rules.

    Thus, item order participates in Tuple identity.

    Tuple and List are distinct DCSTs. A Tuple DCSI and a List DCSI are therefore never equal, even when they contain equal constituent DCSIs in the same order.

    For example,

    (1, 2)

    and

    [1, 2]

    represent distinct DCSIs.

    The canonical representation of a Tuple is

    (item1, item2, ...)

    where each item is represented by its DCV.

    An empty Tuple is represented as

    ()

    A one-item Tuple is represented as

    (item)

    and does not require a trailing comma.

    Tuples may recursively contain DCSIs of any DCST, including other composite DCSTs.

    Set

    The Set DCST represents a finite unordered collection of distinct DCSIs.

    A Set DCSI consists of zero or more DCSIs. The constituent DCSIs may belong to any DCST and need not belong to the same DCST.

    No two members of a Set DCSI may be equal according to their respective DCST equality rules.

    Two Set DCSIs are equal if and only if they contain the same members under DCSI equality, independent of member order.

    Thus, member order does not participate in Set identity.

    For example,

    {1, 2}

    and

    {2, 1}

    represent the same Set DCSI.

    In contrast,

    {1, 1.0}

    contains two distinct members because Integer 1 and Float 1.0 are distinct DCSIs.

    Sets may contain DCSIs of any DCST.

    Because Set has no semantic member order, canonical rendering orders members according to the canonical DataCanon semantic ordering defined by this specification.

    The canonical representation of a nonempty Set consists of the DCVs of its members, in canonical semantic order, enclosed by braces and separated according to the canonical rendering rules.

    The empty Set is represented as

    emptyset

    because

    {}

    represents an empty Mapping.

    Mapping

    The Mapping DCST represents a finite ordered collection of key-value entries.

    A Mapping DCSI consists of zero or more entries in a defined order. Each entry consists of

    • a key DCSI, and
    • a value DCSI.

    Keys and values may belong to any DCST.

    No two entries in a Mapping DCSI may have equal keys under DCSI equality.

    Two Mapping DCSIs are equal if and only if

    • they contain the same number of entries,
    • corresponding keys are equal, and
    • corresponding values are equal.

    Thus, entry order participates in Mapping identity.

    For example,

    {
  "a": 1,
  "b": 2
}

    and

    {
  "b": 2,
  "a": 1
}

    represent distinct Mapping DCSIs.

    Mapping keys are DCSIs rather than strings specifically. For example,

    {
  (0, 0): "Gamma",
  (1/2, 0): "X"
}

    is a Mapping whose keys are Tuple DCSIs.

    The canonical representation of a Mapping consists of its entries in their semantic order, enclosed by braces and separated according to the canonical rendering rules.

    Each entry is represented as

    key: value

    where key and value are the DCVs of the corresponding DCSIs.

    The empty Mapping is represented as

    {}

    UnorderedMapping

    The UnorderedMapping DCST represents a finite unordered collection of key-value entries.

    An UnorderedMapping DCSI consists of zero or more entries. Each entry consists of

    • a key DCSI, and
    • a value DCSI.

    Keys and values may belong to any DCST.

    No two entries in an UnorderedMapping DCSI may have equal keys under DCSI equality.

    Two UnorderedMapping DCSIs are equal if and only if they contain the same key-value entries under DCSI equality, independent of entry order.

    Thus, entry order does not participate in UnorderedMapping identity.

    For example, the sources

    umapping(
  "a": 1,
  "b": 2
)

    and

    umapping(
  "b": 2,
  "a": 1
)

    represent the same UnorderedMapping DCSI.

    Because UnorderedMapping has no semantic entry order, canonical rendering orders entries according to the canonical DataCanon semantic ordering of their keys.

    The canonical representation is

    umapping(
  key1: value1,
  key2: value2
)

    where the entries appear in canonical semantic key order and each key and value is represented by its DCV.

    The empty UnorderedMapping is represented as

    umapping()

    Although an UnorderedMapping has no semantic entry order, its canonical representation has a deterministic order. This canonical ordering exists only to provide a unique DCV and does not become part of the UnorderedMapping DCSI.

    Record

    The Record DCST represents a named structured value consisting of an ordered sequence of named fields.

    A Record DCSI consists of

    • a String name, and
    • zero or more fields in a defined order.

    Each field consists of

    • a String field name, and
    • a value DCSI.

    Field values may belong to any DCST.

    Field names within a Record MUST be unique according to String DCSI equality.

    Two Record DCSIs are equal if and only if

    • their Record names are equal,
    • they contain the same number of fields,
    • corresponding field names are equal, and
    • corresponding field values are equal.

    Thus, both the Record name and field order participate in Record identity.

    For example, records named "Point" and "Vector" are distinct Record DCSIs even if they contain otherwise identical fields.

    Likewise, the fields

    "x": 1
"y": 2

    in that order are structurally distinct from the fields

    "y": 2
"x": 1

    in the opposite order.

    Record is distinct from Mapping. A Record represents a named structure with a defined sequence of named fields, whereas a Mapping represents a collection of associations between arbitrary DCSI keys and values.

    Canonical Representation

    The canonical representation of a Record is

    record(
  "RecordName",
  "field1": value1,
  "field2": value2
)

    where the Record name and field names are String DCVs and each field value is the DCV of the corresponding DCSI.

    Fields appear in their semantic order.

    For example,

    record(
  "Point",
  "x": 1.0,
  "y": 2.0
)

    represents a Record named "Point" with two Float fields named "x" and "y".

    A Record with no fields is represented as

    record(
  "RecordName"
)

    The Record name is semantic data. DataCanon does not assign application-specific meaning to that name and does not interpret it as the name of another DCST.

    For example, "Point" may correspond to a Python class, a Julia type, or some other application-defined concept. Such correspondences are defined by the implementation or application rather than by the Record DCST.

    Arrays

    The Array DCST represents dense, regular multidimensional machine data.

    An Array DCSI consists of

    • an Array type,
    • a finite multidimensional shape, and
    • one element for every position defined by that shape.

    The shape is a finite ordered sequence of nonnegative mathematical integers. The number of entries in the shape is the rank of the Array, and the product of the entries is the total number of elements.

    An empty shape denotes a rank-zero Array containing one element.

    The Array type determines the domain and equality relation of its elements.

    Two Array DCSIs are equal if and only if

    • they have the same Array type,
    • they have the same shape, and
    • corresponding elements are equal according to the equality rule of that Array type.

    Thus, Array type and shape participate in Array identity independently of the values of the elements.

    Arrays are distinct from Lists. A List recursively contains DCSIs. The elements of an Array are instead values of its Array type and are not themselves DCSIs.

    DataCanon does not define a universal type system or coercion policy for Array construction. In particular, DataCanon does not prescribe

    • which additional native Array types an implementation may support,
    • how mixed input parameters are promoted or coerced,
    • how an implementation represents unsupported or implementation-specific Array types.

    These choices are deliberately delegated to the underlying language implementation.

    Applications requiring DataCanon-defined semantic identity for every individual element should use nested Lists rather than Arrays.

    Portable Array Types

    Although Array construction is implementation-dependent, DataCanon Version 1 defines the following portable Array types:

    • bool
    • int8
    • int16
    • int32
    • int64
    • uint8
    • uint16
    • uint32
    • uint64
    • float16
    • float32
    • float64
    • complex64
    • complex128

    These names denote DataCanon Array types rather than types belonging to any particular implementation language.

    The bool Array type contains exactly the two Boolean values true and false. Two bool elements are equal if and only if they represent the same Boolean value.

    The signed and unsigned integer Array types represent mathematical integers within the ranges determined by their respective fixed widths. Two integer Array elements of the same Array type are equal if and only if they represent the same mathematical integer.

    The floating-point Array types represent finite IEEE-754 binary16, binary32, and binary64 values, respectively.

    Two floating-point Array elements of the same Array type are equal if and only if their IEEE-754 bit representations are identical. Positive and negative zero are therefore distinct Array elements.

    NaN and positive and negative infinity are not elements of the portable floating-point Array types in Version 1.

    The complex64 Array type consists of ordered pairs of float32 elements representing the real and imaginary components.

    The complex128 Array type consists of ordered pairs of float64 elements representing the real and imaginary components.

    Two complex Array elements of the same Array type are equal if and only if their corresponding real and imaginary components are equal.

    Conforming implementations MUST provide canonical representations for these portable Array types such that equal portable Array DCSIs produce identical DCVs across implementation languages.

    Implementations MAY support additional Array types. Such extensions do not carry a cross-language DCV guarantee unless standardized by a DataCanon specification.

    Structural Representation

    Arrays containing 1000 elements or fewer are rendered structurally.

    For example,

    array(
  [[1.0, 2.0],
   [3.0, 4.0]]
)

    The bracket notation inside array(...) describes the regular multidimensional structure of the Array. These brackets do not construct DataCanon Lists.

    Structural Array parameters are interpreted by the Array parser rather than by the general DataCanon parser. Their interpretation is therefore part of Array construction rather than recursive DataCanon parsing.

    For example, a portable complex Array may be rendered as

    array(
  [1.0+2.0j, 3.0-4.0j]
)

    The notation

    1.0+2.0j

    is structural Array syntax for a machine complex value. It is distinct from the DataCanon Complex DCST, which uses syntax such as

    complex(1/2, 1/2 * sqrt(3))

    The canonical structural representation is determined by the resulting Array type.

    For example, an implementation may accept

    array([1, 2.5])

    and construct a float64 Array. Its canonical structural representation then uses floating-point elements:

    array(
  [1.0, 2.5]
)

    DataCanon specifies the canonical representation of portable Array types but does not prescribe the implementation-specific construction or promotion rules that produced the Array.

    Binary Representation

    Arrays containing more than 1000 elements are rendered using a canonical binary representation.

    For example,

    array(
  binary(
    "float64",
    (1001),
    "0123456789abcdef..."
  )
)

    The binary representation exists to provide deterministic rendering for machine-scale numerical data while avoiding the cost and size of rendering very large Arrays element by element.

    The canonical binary representation consists of

    • the portable Array type,
    • the Array shape,
    • a little-endian byte stream,
    • C-contiguous element ordering.

    The byte stream is represented as hexadecimal text.

    The Array type is part of Array DCSI identity. Thus, for example, an int32 Array and an int64 Array containing numerically equal elements are distinct Array DCSIs and produce distinct DCVs.

    The structural and binary representations encode the same Array DCST. The choice between them is determined solely by the canonical threshold defined below and does not introduce a semantic distinction between Arrays.

    Structural and Binary Threshold

    The canonical representation of an Array is determined by its total number of elements.

    Arrays containing 1000 elements or fewer use the structural representation.

    Arrays containing more than 1000 elements use the binary representation.

    The threshold depends only on the total number of elements and is independent of dimensionality, shape, and Array type.

    Thus, an Array containing exactly 1000 elements is rendered structurally, while an Array containing 1001 elements is rendered using the canonical binary representation.

    This threshold is part of the DataCanon Version 1 specification. A conforming renderer MUST apply the same rule so that a given portable Array always produces the same DCV.

    Canonical Semantic Ordering

    DataCanon defines a total ordering over DCSIs for the sole purpose of producing deterministic canonical representations of DCSTs whose instances have no semantic order.

    Canonical semantic ordering has no mathematical or application-specific meaning. It does not define comparison operations on DataCanon values and does not participate in DCSI identity except where explicitly required by a DCST.

    For any two DCSIs a and b, exactly one of the following holds:

    a < b
a = b
a > b

    where equality is DCSI equality as defined by the corresponding DCST.

    Ordering Between Semantic Types

    DCSIs belonging to different DCSTs are ordered according to the following fixed DCST order:

    Null
Boolean
Integer
Float
String
Fraction
Coefficient
Complex
Array

Tuple
Set

    This ordering is part of the DataCanon Version 1 specification.

    The relative ordering of different DCSTs has no semantic meaning.

    Null

    The Null DCST contains only one DCSI, so no ordering distinction exists within the Null DCST.

    Boolean

    Boolean DCSIs are ordered

    false < true

    Integer

    Integer DCSIs are ordered according to the usual ordering of mathematical integers.

    Float

    Float DCSIs are ordered by their exact IEEE-754 binary64 bit representations.

    The 64-bit representation is interpreted as an unsigned integer and ordered by increasing unsigned integer value.

    This ordering is not numerical ordering. It exists only to provide a deterministic total order that distinguishes all Float DCSIs, including positive and negative zero.

    String

    String DCSIs are ordered lexicographically by their sequences of Unicode scalar values.

    At the first position at which two Strings differ, the String containing the smaller Unicode scalar value sorts first.

    If one String is a prefix of another, the shorter String sorts first.

    Fraction

    Fraction DCSIs are ordered lexicographically by

    1. numerator,
    2. denominator,

    using Integer ordering for both constituents.

    This is structural ordering rather than ordering by the mathematical rational values associated with the Fractions.

    Coefficient

    Coefficient DCSIs are ordered lexicographically by

    1. scale,
    2. numerator,
    3. denominator,
    4. radicand,
    5. offset.

    The scale and offset are ordered by their exact IEEE-754 binary64 bit representations according to Float ordering.

    The numerator, denominator, and radicand are ordered according to Integer ordering.

    This is structural ordering and does not compare the mathematical values associated with Coefficients.

    Complex

    Complex DCSIs are ordered lexicographically by

    1. real component,
    2. imaginary component,

    using canonical semantic ordering recursively.

    Because the DCST of each component participates in its identity, ordering between components belonging to different DCSTs follows the fixed DCST order defined above.

    Array

    Array DCSIs are ordered lexicographically by

    1. Array type,
    2. shape,
    3. canonical byte stream.

    Portable Array types are ordered according to the following fixed order:

    bool
int8
int16
int32
int64
uint8
uint16
uint32
uint64
float16

    Shapes are compared lexicographically as sequences of nonnegative mathematical integers.

    Canonical byte streams are compared lexicographically as sequences of unsigned bytes.

    The Array ordering is structural and has no numerical interpretation.

    List

    List DCSIs are ordered lexicographically by their constituent DCSIs using canonical semantic ordering recursively.

    At the first position containing unequal DCSIs, the ordering of those DCSIs determines the ordering of the Lists.

    If one List is a prefix of another, the shorter List sorts first.

    Tuple

    Tuple DCSIs are ordered lexicographically by their constituent DCSIs using canonical semantic ordering recursively.

    At the first position containing unequal DCSIs, the ordering of those DCSIs determines the ordering of the Tuples.

    If one Tuple is a prefix of another, the shorter Tuple sorts first.

    Set

    The members of each Set DCSI are first placed in canonical semantic order.

    Set DCSIs are then ordered lexicographically by these canonical member sequences.

    At the first position containing unequal members, the ordering of those members determines the ordering of the Sets.

    If one canonical member sequence is a prefix of another, the Set with fewer members sorts first.

    Mapping

    Mapping DCSIs are ordered lexicographically by their entries in semantic entry order.

    Entries are ordered first by key and then by value using canonical semantic ordering recursively.

    At the first unequal entry, the ordering of that entry determines the ordering of the Mappings.

    If one entry sequence is a prefix of another, the Mapping with fewer entries sorts first.

    UnorderedMapping

    The entries of each UnorderedMapping DCSI are first placed in canonical order according to their keys.

    UnorderedMapping DCSIs are then ordered lexicographically by these canonical entry sequences.

    Entries are ordered first by key and then by value using canonical semantic ordering recursively.

    At the first unequal entry, the ordering of that entry determines the ordering of the UnorderedMappings.

    If one canonical entry sequence is a prefix of another, the UnorderedMapping with fewer entries sorts first.

    Purpose of Canonical Semantic Ordering

    Canonical semantic ordering is used when DataCanon requires a deterministic representation of a DCSI whose DCST does not assign semantic order.

    In particular, it determines the canonical rendering order of

    • Set members, and
    • UnorderedMapping entries.

    Canonical semantic ordering does not add semantic order to these DCSTs. The canonical order of a Set or UnorderedMapping is a property of its representation, not of its DCSI.

    Rendering

    Rendering is deterministic.

    The renderer produces the unique DCV corresponding to a DCSI.

    For any two DCSIs (x) and (y),

    x = y  if and only if  render(x) = render(y)

    where DCSI equality is determined by the corresponding DCST.

    Thus, canonical rendering provides a language-independent textual normal form for DCSI identity.

    Rendering is optimized for

    • determinism,
    • stability,
    • reasonable readability,

    rather than sophisticated document formatting.

    Atomic DCSTs render on a single line.

    Composite DCSTs may introduce structural formatting.

    Rendering canonicalizes representation only. It does not perform mathematical simplification.

    Fingerprinting

    Every DCV possesses a deterministic fingerprint.

    Fingerprints are computed directly from the UTF-8 encoding of the DCV.

    DataCanon Value
       │
       ▼
     UTF-8
       │
       ▼
    SHA-256

    Because equal DCSIs produce identical DCVs, they also produce identical fingerprints.

    The fingerprint is a compact identifier derived from the canonical representation. DCSI equality itself is defined by the corresponding DCST and does not depend on fingerprinting.

    Persistence

    A DCV is itself a complete textual persistence representation of a DCSI.

    Alternative persistence mechanisms may represent the same DCSI while optimizing different engineering objectives.

    For example,

    PersistenceOptimizes
    DataCanonreadability, version control, deterministic representation
    HDF5storage efficiency, random access, compression, high-performance numerical I/O

    A conforming DataCanon persistence mechanism MUST preserve DCSI identity according to the equality rules of the corresponding DCSTs.

    Persistence mechanisms may use different physical representations. Those representations do not participate in DCSI identity.

    Conformance

    A conforming implementation MUST

    • accept valid DCS,
    • construct the DCSI encoded by the source,
    • preserve all distinctions required by the corresponding DCST,
    • implement DCSI equality according to the equality rules of each DCST,
    • render the unique DCV corresponding to a DCSI,
    • preserve DCSI identity across parse/render round trips.

    A conforming implementation is not required to use any particular internal representation for DCSIs.

    Different implementations may therefore represent the same DCSI using different language-specific types or data structures.

    Cross-language conformance is determined by the DataCanon semantic model, not by equality of implementation-specific objects. Implementations representing equal DCSIs MUST produce identical DCVs.

    A conforming renderer MUST always produce a DCV.

    A conforming parser MAY accept noncanonical source provided that parsing and rendering produce the correct DCSI and DCV.
